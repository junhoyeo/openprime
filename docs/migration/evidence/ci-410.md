## Post-merge: shard 3 at `f0c09f100` (run `40436471913`)

Attempt 1 (failed at 02:20Z, before PR #34 merged at 02:24Z): `pa-cli` `acp_mode_e2e::acp_eof_during_settle_exits_and_leaves_resident_subagents` read the child as `queued` (durationMs 60), but the test expected `running`. The same code passed at `a9ae2e3de` (run `40424205627`), in the fork macOS suite, and in the c4c macOS baseline.

Attempt 2 (shard 3 rerun, 02:24-02:35Z) **also failed**. The ACP test passed, but the fork attach-lane test `pa-daemon --lib worker::attach_window_tests::a_direct_attach_streams_an_event_emitted_while_its_snapshot_is_pending` (T4 in `attach.md`) ran over 60 s. It then failed at `attach_window_tests.rs:266` with `the holder is waiting: SendError`, after `Connection reset by peer`. The holder thread gives up only after its 60 s `STEP_BOUND`. So the attach send or the refused `list` barrier was blocked for over 60 s behind the held core lock. That is treated as a possible real intermittent block until root-caused (see the section below). A pass on rerun would not have erased either failure.

Root cause (`/tmp/mig-lead-opus/kickoff-race.md`, read-only analysis): this is an upstream test whose assumption the fork's child status broke. It is not a stuck child.

- Since `3746db134` and `a02416f19`, a child reads `queued` until its detached kickoff prompt is admitted. The kickoff is released by the parent's turn end (Done or DoneAborted), by a positive collect, or by a 60 s fallback. The `prompt_child` RPC then has a 30 s bound, with one retry, and after that a kill and an `error` settle.
- The ACP completion frame is published only after the parent settled. So the roster read raced only the prompt RPC round trip.
- ACP EOF cancels only the parent's own admission. It never cancels children, and the kickoff runs in the parent worker.
- c4c had the same kickoff path but labelled that window `running`. TS also has `queued`, but flips it to `running` before the task prompt.

Fix (parent sign-off for a fork-adapted upstream test): the test now accepts a transient `queued` and polls the roster with a 2-minute fail-closed deadline until it reads `running`. Any settled status fails at once.

A second finding from the same analysis is a fork product regression: no `rlm_child_update` was published for `queued` to `running`. So ACP `subagents` meta and daemon subscribers kept the spawn's `queued` row for a child's whole run. TS emits `running` (`agent-session.ts` 12886-12887). Fix: emit the row at prompt admission (`rlm_children/host.rs`). Red first: `watch_tests::child_updates_surface_through_the_sink` failed on the new `running`-row assertion before the fix and passes after it. `cargo test -p pa-daemon --lib rlm_children` passes 84/84, and fmt and clippy `-p pa-daemon --all-targets -D warnings` are clean.

### Attempt 2: attach-lane flake (open)

A read-only analysis (`/tmp/mig-lead-opus/attach-flake.md`) points to tokio I/O-driver starvation in the test:

- The attach task runs from the LIFO slot of the worker that just left the driver, and blocks that worker on the core lock the test holds (`commands.rs` `require_created`).
- The other workers sleep, so nothing polls the driver. The `list` barrier frame is never read until the holder's 60 s fail-closed release.

The analysis ruled out the peer-grant expiry, which is checked only at `peer_auth`. It also confirmed that the `list` gate path takes no core lock. The product pattern (an attach task taking the std core lock) is the same as at c4c, and product lock holders never wait on runtime I/O.

**This mechanism is not proven.** The repro it predicted (`STEP_BOUND` 5 s plus a 20 ms pause between the attach send and the `list` request) passed 3/3 on macOS (`/tmp/mig-lead-opus/attach-repro-red.log`). So the proposed test-only fix, a driver-keeper thread, is not adopted. The flake stays open and is tracked in [#42](https://github.com/junhoyeo/openprime/issues/42). Next steps:
- run the same repro on Linux, where CI failed;
- if it reproduces there, apply the keeper fix with that red/green proof.
